Optimizing Prometheus & Grafana for High-Cardinality Metrics

Observability is a cornerstone of modern Site Reliability Engineering. However, as microservices scale, the volume of metrics generated can grow exponentially. This often leads to the challenge of high cardinality—where metrics contain labels with a large set of possible values (like user IDs, IP addresses, or UUIDs). This deep dive details how we slashed our Prometheus TSDB memory consumption by 40% and reduced storage billing, while preserving crucial dashboard telemetry.

Understanding the High Cardinality Storm

Prometheus handles timeseries indexes using label combinations. Every unique combination of key-value pairs creates a new timeseries. When developers mistakenly add highly dynamic values as metrics labels, such as:

http_requests_total{method="GET", user_id="8f9a2c3b-5d6e-7f8a..."}

Prometheus has to index millions of streams, which causes its indexing memory to skyrocket and eventually crash with OOM (Out Of Memory) errors. In our multi-tenant Kubernetes cluster, this was causing weekly incidents.

Step 1: Auditing Timeseries Cardinality

We began by executing Prometheus API queries to locate the heaviest metrics in the cluster index. We ran the following query via Prometheus Web Console to find the top 10 metrics taking up the most index space:

topk(10, count by (__name__) ({__name__=~".+"}))

This quickly isolated a few custom application metrics that were exposing unique user session tokens in the labels. These metrics accounted for over 72% of our total timeseries count.

Step 2: Implementing Metric Relabeling Configurations

Instead of waiting for development teams to rewrite their application code, we resolved this immediately at the scraping layer. We configured metric_relabel_configs in our Prometheus agent configuration to drop or replace high-cardinality labels before they hit the database:

metric_relabel_configs:
  - source_labels: [user_id]
    regex: ".+"
    target_label: user_id
    replacement: "anonymous"

This configuration intercept took any unique user_id value and replaced it with the static string "anonymous", consolidating millions of individual streams back into a single timeseries stream while keeping total call rate statistics intact.

Step 3: Alerting on Cardinality Spikes

To prevent future occurrences, we set up proactive alerts. We created a Prometheus alerting rule that triggers if the total index size or ingestion rate spikes unexpectedly:

groups:
- name: cardinality_alerts
  rules:
  - alert: PrometheusTimeseriesCountSpike
    expr: prometheus_tsdb_head_series > 1500000
    for: 15m
    labels:
      severity: warning
    annotations:
      summary: "Prometheus timeseries count exceeded limits"

The Result

After applying the configurations, the results were dramatic:

  • Memory Usage: Dropped by 40% immediately, restoring stability to the monitoring pods.
  • Disk Space & Retention: Disk storage growth slowed, saving substantial monthly EBS volumes costs.
  • Query Performance: Dashboard loading speed in Grafana went from 8.2 seconds down to less than 400 milliseconds.

High cardinality is a common hurdle, but with structured index auditing, proactive relabeling policies, and strict developer guidelines on label schemas, you can keep your observability robust and cost-efficient.
